# Songbook PDF CORS — staging verification, 2026-11-07

## Reproduction and cause

The staging bucket had no CORS configuration, although the repository already
contained `cors.json`. The reported SVGs and the saved trumpet cover returned
HTTP 200 without `Access-Control-Allow-Origin` for either staging Hosting domain.
This prevents browser fetches and canvas image loading despite valid Storage
permissions and download tokens.

## Fix

Applied the existing `cors.json` directly to
`gs://cadernin-staging.firebasestorage.app`. The policy allows cross-origin GET
requests from any origin, matching the existing public-readable assets. No
object contents, download URLs, Storage rules or Firestore records were changed.

Both deploy workflows now configure Cloud SDK after authentication and apply
`cors.json` to their environment's bucket before Firebase deployment. The
runbook includes the manual command and notes that object cloning does not copy
bucket CORS configuration. Production configuration was not changed during this
verification.

This work branches from `fix/storage-project-authorization` (PR #402).

## Verification

- Staging bucket metadata matches the tracked CORS policy.
- All seven reported assets (six SVGs and the saved cover) returned HTTP 200 with
  valid CORS headers from both `firebaseapp.com` and `web.app`: 14 checks passed.
- In isolated headless Chrome, authenticated as the songbook's existing owner,
  opened `/projects/ola-mundo/songbooks/bloco-da-chuva` on the reported
  `firebaseapp.com` origin and generated its trumpet PDF through the actual UI.
- Downloaded PDF: 757,854 bytes, valid `%PDF-` signature; six SVG responses and
  one cover response; zero browser errors during generation.
- Temporary browser profiles containing authentication state were removed.
- Both workflow YAML files parse and configure CORS before deployment;
  `git diff --check` passes. No application code changed, so builds and unit
  tests were not repeated. The GitHub workflows themselves were not executed.

## Separate finding

`drawSvg` currently logs and swallows asset-fetch errors, which can produce
incomplete PDFs when assets fail for other reasons. That behavior is unchanged;
the successful browser check verified all expected asset requests for this PDF.
