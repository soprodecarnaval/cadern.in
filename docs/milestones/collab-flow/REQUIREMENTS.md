# Collaborative features

## Requirements
- all deletes are soft deletes for traceability. _REVISION objects can't be deleted, they're a version linked list. this is important for the abstractions in place
- USER can be member of multiple PROJECTS
- PROJECT is composed of MEMBERS, REVISIONS(SCORES) and SONGBOOKS
- REVISIONS form a linked list REVISION -> PREV(REVISION) -> PREV(PREV(REVISION)), etc.
- SONGBOOKS are the products of the PROJECT
- a SONGBOOK is composed of a pointer to a SONGBOOK_REVISION. non-members can only access the latest revision.
- artifacts of SONGBOOKS are INSTRUMENT_SONGBOOKS
  + INSTRUMENT_SONGBOOK will contain the parts in these SONGBOOK_SCORES for a certain instrument
  + all INSTRUMENT_SONGBOOK keep consistent index numbering for SONGBOOK_SCORE (as implemented today)
- USERS have a ROLE in a PROJECT
  + OWNER > ADMIN > EDITOR > REVIEWER
  + higher levels can do all the the lower levels can do plus some additional capabilities
- REVIEWERS can make REVIEW_COMMENTS on REVISIONS
  + REVIEW_COMMENTS can be seen on the REVISION page by other REVIEWERS
  + REVIEW_COMMENTS can be marked as solved
- EDITORS can upload new REVISIONS to a SCORE in a PROJECT and new SCORES to a PROJECT
- ADMINS can manage SCORES (change metadata), SONGBOOKS (change cover image, and manage MEMBERS of a PROJECT (add/invite/assign reviewer and editor roles)
- OWNERS can completely manage SCORES (delete), SONGBOOKS (publish, unpublish and delete) and PROJECTS (delete, delete members, assign admin role)
  + deleting a SONGBOOK does not delete its SCORES.
- not necessarily all SCORES belonging to a PROJECT are part of a SONGBOOK
- non-member users can fork a SCORE off a project on a specific REVISION
  + its REVISION object should trace its lineage back
